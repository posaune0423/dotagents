# 再現性の確認

新しい題材で口調を確認するためのケース。以下は架空の状況であり、実際に実施済みの作業ではない。
実行時は `SKILL.md`、`references/writing-format.md`、該当する媒体の例を読み、各ケースの文案を作る。

## ケース

1. **Slack / 受領**: 相手が仕様を確認してくれた。感謝し、自分でも後ほど確認する予定を伝える。まだ確認はしていない。
2. **Slack / レビュー依頼**: PR のリンクは `<PR_URL>`。急ぎではなく、お手隙でレビューをお願いする。締切は設定しない。
3. **GitHub / 修正返信**: 指摘のあった変数名は修正済み。相手にお礼を伝える。テスト結果は与えられていない。
4. **GitHub / 別対応の相談**: 提案は理解したが、今回の変更範囲が大きくなるため別 PR で対応したい。決定として宣言せず相談する。
5. **Slack / 技術相談**: 通知の polling 間隔を検討中。realtime 性が必要かは未確認。負荷を抑えるため 1 分間隔を候補として提案する。
6. **Slack / 遅延連絡**: 対応が遅れている。完了日時は不明。短くお詫びし、状況を確認して共有する予定を伝える。
7. **Slack / 作業報告**: 稼働終了を伝える。今日行ったのは「レビュー」「通知 UI の文言修正」「再接続処理の調査」。調査は未完了。
8. **編集 / 事実保持**: 「検証環境に反映した。本番はまだ。手元の Chrome では確認した。Safari は未確認」を自然な仕事の口調にする。

## 新題材での追加ケース

基本ケースは例文と近いため、以下で別の状況への適用も確認する。生成文は事前に用意しない。

9. **GitHub / 調査段階の相談**: reviewer からライブラリの置き換えを提案された。
   既存 config の調査だけ済んでおり、置き換え先はまだインストールも評価もしていない。
   先に現在の config を修正する方針でよいか相談する。
10. **Slack / チーム間の依頼**: schema のある field を nullable にするか BE の判断を確認したい。
    FE は mock で進めており、BE との接続はまだ。締切や宛名の指定はない。
11. **Slack / 重大な状況共有**: 決済結果を調査中。影響件数、原因、復旧見込みは分からない。
    確認できている調査状況を伝える。明るい感嘆符や絵文字は使わない。
12. **編集 / 不同意の保持**: 「案Aには同意していません。表示密度が高すぎるのが懸念です。
    案Bを試してから判断したいです。」を自然にする。同意や承認に変えない。

## 評価観点

- 事実保持: 予定を完了扱いにしない。検証結果・期限・リンク・相手の名前を足さない。媒体に合うだけの省略に留める。
- 場面適合: Slack の依頼、技術相談、短い PR 返信、作業報告で文量と距離感を変える。
- 声の再現: 短い「です・ます」を基調とし、自然な「こちら」「一旦」「〜ですかね？」や感嘆符を必要な場所で使う。全部入りにはしない。
- 自然さ: 書き出しの説明、過剰な敬語、装飾見出し、毎回の絵文字、わざと作った誤字を避ける。
- 相談の保持: 異論は理由と相談にする。疑問を断定へ書き換えない。
- 原文からの独立: 過去の人物・案件・日付・非公開情報を新しい文案へ持ち込まない。

事実保持か相談の保持に失敗した場合は、口調が似ていても不合格。
口調の評価は人手の判断であり、点数や一致率を客観的な本人判定として扱わない。

## 文末・構成の改訂に使うケース

13. **Slack / 温度のある受領**: 普段やり取りする同僚が QA 項目をすぐ追加してくれた。
    感謝を伝え、自分の確認は後ほどの予定として返す。
14. **Slack / 追加の依頼**: 同僚に二件レビュー依頼をしたあと、さらに `<PR_URL>` のレビューをお願いする。
    相手は忙しく、急ぎではない。締切は指定されていない。
15. **Slack / 認識の更新**: response の新しい field が追加済みだと勘違いしていた。
    BE が来週追加すると理解したので、FE は当面 mock のまま進める。軽い認識違いとして返す。
16. **GitHub / 用途と直接の問い**: 削除予定の field を pagination で使いたい。削除する理由を聞く。
    相手を責めず、無条件の同意や削除の承認に変えない。
17. **Slack / 必要十分な案**: client cache を考えていたが永続化は不要。
    まず in-memory cache にすることを提案し、同意を求める。実装はまだしていない。
18. **GitHub / 必須の変更**: 監査で必要なので、失敗時にも request ID をログに残す修正を依頼する。
    任意の改善や将来の検討に弱めない。現在の原因や実装詳細は不明。
19. **Slack / 報告の素っ気なさ**: 稼働終了。今日行ったタスクはレビュー、監査ログの調査、文言修正。
    調査は継続中。タスクの行ごとに感嘆符や絵文字を付けない。
20. **Slack / 複数制約の説明**: キー変更には旧クライアントへの影響がある。更新タイミングも揃わない。
    そのため互換期間を設けて新旧両方を受ける案を相談する。期間の長さと可否は未決定。
    simple にしつつも二つの制約と相談であることを落とさない。

追加の評価観点:

- 「！」・絵文字・間が反応や依頼の役割と合っているか。単に記号を多くすれば合格ではない。
- 短い受領や依頼を不必要に事務的にしていないか。使わない文の存在も保っているか。
- 対象と操作、判断に必要な一段の理由があるか。抽象的な「改善・検討」で置き換えていないか。
- 追加、留保、前提を受けた行動で接続詞を使い分け、全てに同じ書き出しを付けていないか。
- 必須の依頼は明確で、未決定の案は相談として残っているか。
- 改訂前後の比較は定性的に行い、本人らしさの数値的改善を捏造しない。
