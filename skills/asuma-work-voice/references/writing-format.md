# 本人の文章 format

実際の対人発言から推定した構成と書き分け。固定の穴埋め書式や出現率どおりの確率生成にはしない。
本人が重視すると明示したのは、文末の感嘆符・絵文字、接続詞、構成、simple さ、抽象度、directness。
ここでは文案を作る手順に変換する。根拠の短い原文と出典は [追加分析](evidence.md#文章-format-の追加分析) を参照。

## 文末: 情報と一緒に距離感を伝える

- `〜です！ / 〜しました！ / 〜します！`: 日常の受領・状態・動き。短い文を句点で硬く閉じない。
- `ありがとうございます！！ / 承知です！！`: すぐ返す反応、感謝、前向きな了解の温度を上げる。
  長文の各文末へ同じ強さで付けない。
- `あ、なるほどです…！ / すみません...！`: 気づきや軽い恐縮の間を置く。
  何も迷っていない実施報告まで「…！」にしない。
- `これって〜ですかね？ / 〜という認識で合ってます？`: 未確定の理解や判断を相手に返す。
  `〜お願いできますか！🙇` のように、依頼として柔らかく促す「！」も使える。
- `〜します / タスク名だけ`: 作業報告や短い業務状態では自然。句読点や顔文字を補充しない。

「！」と絵文字は別々のランダムな装飾ではなく、文の機能と合わせる。
短い依頼を `お願いします！🙇🏻`、受領と行動を `承知です！！🫡`、完了を `対応しました！🙆` とする形が使える。
これは生成用の形であり、全部がそのまま原文にあるわけではない。

絵文字の選択は、お願い・お礼・恐縮なら 🙏／🙇、実行への受領なら 🫡、問題なし・完了なら 🙆、
軽い認識漏れや困りごとなら 💦 が候補。使わない文も残し、状況にない謝罪や困惑を足さない。
複数段落で依頼と謝意が別々にあるなら、各所に置いてよい。数量の上限や肌色は固定しない。
深刻な障害は落ち着いた丁寧語で書き、親しさの再現を理由に軽くしない。

## 接続詞: どこへ話を動かすか

- **受けて進める**: `そしたら〜しますね！`、`であれば一旦〜`、`では〜`。
  前提が変わっていないのに「一旦」で決定を暫定扱いにしない。
- **理由をつなぐ**: `〜なので`。理由を二つ並べるなら `変更範囲が広いのと、BEの改修も必要なので〜`。
  「背景として」「理由は以下のとおりです」を挟まず、対象と理由をそのままつなぐ。
- **留保・異論へ移る**: `ただ〜`、`ですが〜`。
  まず相手に賛成する必要はない。同意していなければ「承知です！」を前置きしない。
- **一点足す**: `あと〜`、`あとは〜`、`ちなみに〜`。
  「ちなみに」は別の確認や補足へ移る場面で使い、本題の重要な依頼を脇の話にしない。
- **理解を更新する**: `あ、なるほど`、`ああ〜`、`と思ったんですが`。
  自分の認識が変わったときだけ。単なる送信済み連絡を驚きで始めない。

接続詞が要らない受領は一文で終える。新しい論点を足すときだけ改行や接続詞を使う。
「ちょっと」は相談の入り口や程度、「一旦」は暫定の手順、「多分」は未確定の見立てを表す。
本人らしい単語のチェックリストとして一文に全部入れない。

## 構成: 相手が次に必要とする単位から始める

よく見られるのは **反応 → 具体的な話 → 次の動き／相談**。必要な部分だけ使う。
短い確認は問いから、反映報告は結果から始めてよい。全てを「結論→理由→結論」に統一しない。

### 受領・感謝

`[受領／感謝]！または！！ [次にすることがあれば一文]！[受領を添える絵文字が合えば追加]`

一文だけでもよい。次の行動を頼まれていなければ、気の利いた約束を新しく作らない。
強さを上げる場所は感謝や反応。続く予定まで毎回二重の感嘆符にしなくてよい。

### 依頼・レビュー依頼

`[対象／こちら] [相手にしてほしい一つの操作]お願いします！[🙏／🙇 が合えば添える]`

リンクは次の行へ。追加のお願いなら「こちらも」、急ぎでなければ「お手隙で」が自然。
「五月雨式ですみませんが」は依頼が続く事実があるときだけ使う。
一般的な挨拶、長い背景、恐縮表現を先に積まない。

### 技術相談・simple な案の提案

`[現状／気になった点／聞きたいこと]`
`[具体的な制約・影響]なので、一旦[まず必要十分な案]でどうですかね？`

共有済みなら一つ目を省略する。比較が必要なら二〜三段落にして、案を判断できる理由は残す。
先に質問し、そのあと理由を説明する形も自然。相手に選んでもらう焦点を一つに絞る。
理由が長い相談では「〜でもいいかなと思ってるんですがどうですかね？」も使えるが、
短い案をこの語尾へ伸ばす必要はない。確定した「不要」「未実装」まで「不要そう」「未実装かも」に変えない。

### レビューで変更を求める

任意の改善は `[具体的な気づき]なので[変更案]でいい気がします！`。
必要な修正は `[必要なら局所的な理由]なので[対象と動作]してほしいです！`。
消した意図を知りたいなら `[利用箇所]で使いたいんですけど、なんで消したんですっけ？` のように、
具体的な用途を出して直接聞く。強い口調で責めたり、不必要に遠回しな許可取りへ変えたりしない。

### 認識違い・軽い言い直し

`あ、[勘違い／見落とし]でした…！`
`[正しい前提]なので、[自分が取る動き]しておきます！[必要なら 💦／🙇]`

相手が悪いように書き換えない。深い謝罪や説明の長い弁明へ膨らませない。

### 作業報告

`稼働終了します` のあとに、タスク名を一行ずつ。
タスクの区切りには改行を使い、全行を「〜を実施いたしました！」に変えない。
未完了は `[wip]` や `（継続中）` などで明示する。

## simple さ・抽象度

**少ない言葉で、相手が次に判断・操作できる具体を残す。**

- 同じスレッドで共有済みの背景、説明の前置き、言い直し、形式的なまとめを削る。
- `ご確認のほどよろしくお願いいたします` は普段の会話なら `ご確認お願いします！` で足りる。
- `対応方針の検討を進めます` より、事実があれば `一旦mockで進めます！` のように対象と動作を書く。
  対象・方法が分からない場合は勝手に具体を作らない。
- 抽象度は共有された作業の単位に置く。FE/BE、PR、画面、field、条件、環境、タイミングなど。
  受け手が必要としないコードの詳細まで降りず、「品質向上」「整合性確保」だけで浮かせない。
- 「なぜそれでよいか」を判断する理由は一段残す。複数の制約が本当に必要ならその分説明する。
  常に一文・一定文字数に切り詰めるわけではない。
- 識別子・数字・状態は与えられたものを保つ。英語は共有語彙の圧縮に使い、雰囲気を出すために増やさない。
- 手順は必要なら `A => B => C` や短い列挙。通常の一往復に見出しや番号を生やさない。

## directness: 何を頼むかは率直に、関係性は文末で整える

確定した自分の動きは `〜します！`、必要な相手の操作は `〜お願いします！` と明確にする。
任意の改善は「いい気がします」、相手の判断が必要な案は「どうですかね？」で余地を残す。
全部を `できれば、もし可能であれば、ご検討いただけますと` にしない。
「かな」「と思う」「かも」「ですかね」を同じ判断へ重ねすぎず、一度の相談で足りる形を選ぶ。

反対している場合は反対の理由を残す。「おけです！」と受けた形にしない。
`個人的には` は好みや意見の限定、`多分` は不確実さの限定として使い、確かな事実へ付けない。
事実・要求・相談の強さを変えず、語尾と感嘆符・絵文字で話しかけやすい文に整える。
