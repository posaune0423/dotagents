# Where These Rules Come From

Each rule in `SKILL.md` is traceable here, so it can be argued with rather than obeyed. Sources are marked **primary** when the prescription was read on the originating site or paper, and **secondary** when it was reached through a summary.

## Where the sources disagree

**Legends.** The C4 checklist wants a key on every diagram. The `artifact-diagramming` guidance says a legend earns its place only when the same encoding repeats, and otherwise the meaning belongs on the mark. These address different artifacts: C4 is written for a standalone published architecture diagram, `artifact-diagramming` for a figure embedded beside its own prose. This skill resolves it by putting meaning on the mark, and adding a key when an encoding repeats or the figure has to travel without its text.

**Decoration.** Tufte's data-ink prescription says strip it. Bateman et al., "Useful Junk?" (CHI 2010), found embellished charts were recalled _better_ with no loss of comprehension accuracy. This skill therefore argues against decoration only on the grounds of precision and mechanism legibility, and makes no claim that decoration harms understanding or memory.

**A fixed order.** Diátaxis states plainly that it "offers a set of principles - it doesn't offer a formula", and critics of the Minto pyramid note that rigid answer-first framing fits poorly with exploratory work. Hence the overview-first order in this skill is a default with a documented escape hatch, not a mandate.

**Always leading with one overview diagram.** Simon Brown argues the opposite for non-trivial systems: trying to fit the whole story on one diagram produces clutter, so split from the start, and only draw a component diagram at all "if you feel they add value". Kruchten likewise holds that not all views are necessary. This skill keeps a diagram in the overview because that is what the user asked for, but explicitly does not require it to cover the whole system.

## What this skill deliberately does not claim

- **No node-count cap.** An earlier draft asserted twelve. Nothing in Miller, Cowan, Tufte, the C4 material, the UML-comprehension literature, or any diagramming tool's documentation supports a specific number. The closest primary anchor is Brown's hedged "20+, perhaps fewer".
- **No blanket ban on restating the diagram.** Mayer & Johnson's 2008 revision of the redundancy principle found that short, spatially integrated redundant text improved retention. The rule here targets long prose walkthroughs, not labels and captions.
- **Nothing from Mayer's modality or temporal-contiguity principles.** Both are defined for narrated animation and have no analogue in an all-written document, so citing them here would be unfounded.
- **No published evidence specific to software architecture diagrams read by expert engineers.** The software-engineering evidence found was UML class-diagram comprehension work. The expertise-reversal argument applied to code explanation is an inference, not a replicated result.
