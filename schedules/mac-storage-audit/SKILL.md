---
name: mac-storage-audit
description: Audit local macOS storage read-only and produce a periodic disk-pressure report. Use for local storage inventory; do not use for cleanup or deletion.
---

Macのストレージを毎日読み取り専用で監査し、日本語で人間が一目で判断できるレポートをこのタスクに返してください。対象はAPFSの内蔵コンテナと `/Users/asumayamada` 配下です。

## 安全ルール

- 監査対象のファイル、ディレクトリ、Dockerデータ、キャッシュ、スナップショットを削除・移動・圧縮・変更しないでください。
- `docker prune`、`rm`、`trash`、キャッシュ削除、写真操作は実行禁止です。
- 許可される書き込みは、ローカル状態ディレクトリ `/Users/asumayamada/.local/state/dotagents/mac-storage-audit/` に日次サマリーJSON、全件インベントリJSONを保存し、`latest.json` を更新することだけです。この出力先をGitリポジトリや同期フォルダへ変更しないでください。
- 権限不足の場所は迂回せず、未計測として明記してください。写真ライブラリなどプライバシー保護領域の内容やファイル名は報告しないでください。

## 計測

1. `diskutil apfs list` と `df` で内蔵APFSコンテナの総容量、使用量、空き、使用率を取得してください。
2. `du -x` を使い、内蔵Data volumeの `/System/Volumes/Data` を同一ファイルシステム内で網羅的に測定してください。まず `/System/Volumes/Data` 直下（Users、Applications、Library、privateなど）を個別に測り、1GB以上のディレクトリは原因が判別できる粒度まで再帰的に掘ってください。`/Users/asumayamada` 配下は隠しディレクトリを含めて全ルートを測定し、Private、Work、Library、`.cache` だけに限定しないでください。1本の `du` が長時間停止する場合は子ディレクトリ単位へ分割し、未計測の場所とエラーを記録してください。
3. 大きいルートは固定の深さで打ち切らず、1GB以上を占める枝を原因が判別できる粒度まで掘ってください。特にDocker、リポジトリの `build`、`target`、`.next`、`node_modules`、AIモデル、開発ツールキャッシュ、worktree、データベース、評価データ、小ファイルが大量に集積したディレクトリを区別してください。親子を同時に総量へ加えず、二重計上しない階層として保持してください。
4. `fd -HI --one-file-system` と `stat` を使い、アクセス可能な `/System/Volumes/Data` 全体から100MB以上の通常ファイルを件数上限なしで抽出してください。`/System/Volumes/Data/Volumes` など別ファイルシステムのmount pointには入らず、未走査領域として記録してください。ファイルごとに論理サイズと `du` による実割当サイズ、最終アクセス・更新日時、パスを記録してください。`Docker.raw`、疎ファイル、APFS cloneは見かけの論理サイズではなく実割当サイズをディスク圧迫の判断に使ってください。Spotlightの `mdfind` は補助として使えますが、隠しファイルを漏らすため単独の結果を完全な一覧として扱わないでください。秘密ファイルの中身は読まないでください。
5. `tmutil listlocalsnapshots /` と `diskutil apfs listSnapshots /` でローカルスナップショットの有無だけ確認してください。
6. Dockerが応答する場合だけ `docker system df` を読み取り専用で実行し、Images、Volumes、Build Cacheの総量とRECLAIMABLEを取得してください。
7. `/Users/asumayamada/.local/state/dotagents/mac-storage-audit/latest.json` があれば前回との差分を計算し、今回のサマリーを `YYYY-MM-DD.json` と `latest.json`、100MB以上の全ファイル一覧と1GB以上のディレクトリ階層を `full-inventory-YYYY-MM-DD.json` に保存してください。件数を切り捨てず、走査対象数・成功数・権限エラー数も記録してください。同日のファイルがある場合は安全に更新し、履歴の他の日付は削除しないでください。

## 最終利用が古い項目の判定

1. 100MB以上として抽出した全ファイルと、1GB以上の全ディレクトリについて、`mdls` の `kMDItemLastUsedDate` と `kMDItemFSContentChangeDate`、`stat` のアクセス日時・更新日時を取得してください。件数上限は設けないでください。
2. 最終利用日は `kMDItemLastUsedDate`、アクセス日時、更新日時を突き合わせ、削除に慎重な方向で最も新しい信頼可能な日時を採用してください。SpotlightはCLIや一部アプリの読み取りを記録しない場合があるため、Spotlight日付が古くてもアクセス日時が新しければ古い候補にしないでください。値がnull、作成日と同一、監査によって更新された可能性がある場合や日時同士が矛盾する場合は「不明」または「低確度」とし、削除提案ではなく要確認にしてください。アクセス日時だけで人が最後に開いた日だと断定しないでください。
3. 90〜179日利用の証拠がない項目を「長期未使用候補」、180日以上を「非常に古い候補」としてください。再生成可能な `build`、`target`、`.next`、`cache` は60日以上でも候補にできます。90日未満は原則として古い候補にしないでください。
4. 削除提案の前に読み取り専用で安全性を確認してください。通常ファイルは `lsof` で現在開かれていないか確認してください。Gitリポジトリやworktreeは `git status --porcelain`、現在ブランチ、upstreamとの差分、`git worktree list` を確認し、dirty、未追跡、未push、現在使用中の可能性があれば削除候補ではなく「要確認」にしてください。Dockerはactive containerや参照中imageを削除候補にしないでください。データベース、評価結果、写真、Codex sessionsは古さだけで削除候補にしないでください。
5. 提案を「削除提案」「アーカイブ提案」「保持」に分け、各項目へサイズ、最終利用の根拠、経過日数、確度（高・中・低）、安全性の理由、復元・再取得方法、見込解放容量を付けてください。
6. キャッシュやビルド成果物は再生成・再ダウンロード可能な場合だけ「削除提案」にしてください。ソースコード、Git pack、DB、バックテスト・評価データ、worktreeは内容確認なしで削除提案にしないでください。
7. 実行コマンドを示す場合も参考情報としてだけ記載し、絶対に実行しないでください。削除・Trash移動・Docker prune・Git worktree removeにはユーザーの明示承認が必要です。

## 固定レポート形式

- タイトル: 「Macストレージ日次レポート YYYY-MM-DD HH:mm JST」
- 先頭に1行判定: 正常（80%未満）、注意（80〜89.9%）、危険（90%以上）
- サマリー: 総容量・使用量・空き・使用率・前日からの増減
- 「どこが大きいか」: 上位10領域をGBと割合付きの横棒テキストグラフで表示
- 「昨日から増えた場所」: 増加量上位5件。初回や比較不能ならその旨を明記
- 「ボトルネック」: 上位10件を、サイズ、前日差、最終更新、理由の短い説明付きで一覧化
- 「巨大ファイル」: 1GB以上のファイルは全件表示し、100MB〜1GBは種類・親ディレクトリ・経過日数帯ごとに集計して表示する。全件データは `full-inventory-YYYY-MM-DD.json` に保存した件数と場所も示す
- 「長期間使っていない候補」: 100MB以上の全件から抽出し、最終利用日、経過日数、確度を付け、90日以上と180日以上を分ける。件数上限は設けないが、同じ再生成可能キャッシュ配下は親単位にまとめ、内訳件数と総量を示す
- 「削除・アーカイブ提案」: 削除提案・アーカイブ提案・保持の3区分。各候補に見込容量、根拠、復元方法を付ける
- 「注意・計測漏れ」: 権限エラー、最終利用日の不確実性、未走査領域、macOS Storage分類とのズレを記載
- 最後に「今日確認するならこれ」の候補を1〜3件だけ示す

macOSのDocumentsは `~/Documents` フォルダそのものではなく、ホーム内で他カテゴリに入らないファイル群も含むため、Finderのカテゴリ値と実パスの測定値を同一視しないでください。Photosは写真ライブラリだけを別扱いにし、iCloud Photosの有効化状態を端末から推測しないでください。

文章は短く、数値は原則GBで小数1桁、差分は `+` または `-` を明示してください。削除を提案するときも実行せず、必ずユーザーの明示承認が必要だと書いてください。
